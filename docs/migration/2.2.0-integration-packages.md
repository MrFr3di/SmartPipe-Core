# Migrate integration packages to SmartPipe 2.2.0

This guide covers the intentional migration from the 2.1.2 broad integration
package to the 2.2.0 leaf-package layout. Read it with the constraints in
[ADR-0001](../adr/0001-smartpipe-2.2-package-boundaries.md), the compatibility
quarantine in
[ADR-0002](../adr/0002-smartpipe-2.2-legacy-compatibility-quarantine.md), the
[ADR-0004](../adr/0004-smartpipe-2.2-breaking-migration.md), the
[architecture plan](../maintainers/2.2.0/plans/architecture-plan.md), and the
[branch/review policy](../maintainers/governance/2.2.0-branch-and-review-policy.md).

## Choose a package

New applications should reference only the leaves they use. Package references
bring `SmartPipe.Core` transitively where required.

| Scenario | Packages to reference |
|---|---|
| Pipeline registration and keyed services | `SmartPipe.Extensions.DependencyInjection` |
| Generic Host orchestration or health checks | `SmartPipe.Extensions.Hosting`, `SmartPipe.Extensions.HealthChecks` |
| Telemetry | `SmartPipe.Extensions.OpenTelemetry` |
| JSON or CSV files and framing | `SmartPipe.Extensions.Json`, `SmartPipe.Extensions.Csv` |
| HTTP transport and JSON codecs | `SmartPipe.Extensions.Http`, optionally `SmartPipe.Extensions.Http.Json` |
| Dapper, EF Core, Mapster, or PostgreSQL-native COPY/LISTEN | `SmartPipe.Extensions.Dapper`, `SmartPipe.Extensions.EntityFrameworkCore`, `SmartPipe.Extensions.Mapster`, or `SmartPipe.Extensions.PostgreSql` |
| Resilience, transforms, validation, logging, or channels | `SmartPipe.Extensions.Polly`, `SmartPipe.Extensions.Transforms`, `SmartPipe.Extensions.DataAnnotations`, `SmartPipe.Extensions.Logging`, or `SmartPipe.Extensions.Channels` |
| Reusable framework-neutral test primitives | `SmartPipe.Testing` in test projects only |

`SmartPipe.Extensions` remains available as the convenience bundle and
compatibility facade for an application that intentionally wants the complete
bundled runtime integration set. It has 17 direct SmartPipe dependencies:
`SmartPipe.Core` plus the 16 runtime integration leaves. Its closure contains
18 SmartPipe IDs including the facade. `SmartPipe.Testing` is
published separately and is excluded from that runtime graph.
`SmartPipe.Extensions.PostgreSql` is a runtime leaf that is deliberately not part
of the bundle: it is optional, the facade carries no type forwarder for it, and
no required package edge points at it.

For retained moved types, [ADR-0001](../adr/0001-smartpipe-2.2-package-boundaries.md)
uses facade type forwarding where binary identity permits it and thin obsolete
wrappers only for composites that cannot be forwarded safely. Source and
2.1.2 binary consumers validate those retained moves. The
[ADR-0002](../adr/0002-smartpipe-2.2-legacy-compatibility-quarantine.md) legacy
DI/Hosting/Health cluster stays physically in `SmartPipe.Extensions` under
`obsolete-wrapper` ownership for 2.2.0 and is not an SP220-17 removal.

## HTTP migration (SP220-13)

Under [ADR-0004](../adr/0004-smartpipe-2.2-breaking-migration.md), SP220-13
removed `HttpSelector<T>`, `HttpClientFactorySelector<T>`, `HttpSink<T>`,
`HttpClientFactorySink<T>`, and `HttpSelectorStreamingMode` from
`SmartPipe.Extensions`. They have no replacement wrappers or type forwarders;
consumers update and recompile. The ownership matrix records each as `removed`,
and the facade carries only the five matching `CP0001` ApiCompat suppressions.

| 2.1.2 usage | 2.2.0 replacement |
|---|---|
| `HttpSelector<T>` / `HttpClientFactorySelector<T>` | `HttpPipelineComponents.Source` or `FromHttp` (`SmartPipe.Extensions.Http`) with `HttpJsonResponseReaders.JsonArray`/`Ndjson`, or `FromHttpJsonArray`/`FromHttpNdjson` (`SmartPipe.Extensions.Http.Json`) |
| `HttpSink<T>` / `HttpClientFactorySink<T>` | `HttpPipelineComponents.Sink` or `ToHttp` with `HttpJsonRequestContent.Post`, or `ToHttpJson` |
| `ResiliencePipeline` constructor argument | An `HttpClient` handler, the Core stage policy, or the `SmartPipe.Extensions.Polly` decorator; the adapter never retries |
| `useTraceIdIdempotencyKey: true` | A pure `idempotencyKeySelector` returning a stable key |
| `HttpSelectorStreamingMode.JsonArray` / `.Ndjson` | Choose `HttpJsonResponseReaders.JsonArray` or `HttpJsonResponseReaders.Ndjson` |
| Reflection JSON constructors | Source-generated `JsonTypeInfo<T>`; no reflection fallback |

The facade references both HTTP leaves and no longer depends directly on
`Microsoft.Extensions.Http`. The direct, trimmed, and NativeAOT consumer scenarios
`http-direct`, `http-trim`, `http-nativeaot`, `http-json-direct`,
`http-json-trim`, and `http-json-nativeaot` exercise the leaves without the
facade.

## Polly migration (SP220-14)

Under [ADR-0004](../adr/0004-smartpipe-2.2-breaking-migration.md), SP220-14
removed `SmartPipe.Extensions.Transforms.PollyResilienceTransform<T>` from
`SmartPipe.Extensions`. Its Polly callback returned
`StageResult<T>.Success(envelope.Payload)` without running an inner transform,
so retries and timeouts never covered real work. There is no wrapper or
forwarder: consumers update and recompile. The ownership matrix records the type
as `removed`, and the facade carries one matching `CP0001` ApiCompat
suppression.

| 2.1.2 usage | 2.2.0 replacement |
|---|---|
| `new PollyResilienceTransform<T>(ResiliencePipeline pipeline, logger)` | `PollyPipelineComponents.Decorate` with Core's `Transform(stageKey, component)`, or `new PollyTransformDecorator<TInput,TOutput>(inner, pipeline, ownership)` |
| Untyped `ResiliencePipeline` | A typed, application-owned `ResiliencePipeline<StageResult<TOutput>>` |
| Timeout and broken-circuit exceptions returned `Transient` failures in category `"Resilience"`; `InvalidOperationException` returned a `Permanent` failure | Final exceptions are rethrown unchanged; supply `PollyTransformDecoratorOptions.ExceptionMapper` to turn the final non-cancellation exception into a failure result |
| Optional `ILogger<PollyResilienceTransform<T>>` | None; the decorator logs nothing |
| `Microsoft.Extensions.Resilience` pulled in by the facade | `Polly.Core` only; add `Polly.Extensions` or `Polly.RateLimiting` yourself when you need a registry, telemetry, or rate limiting |

Ownership of the inner transform is explicit (`Borrowed` or `Owned`) on the
constructor and on both `Decorate` overloads. The inner transform runs once per
Polly attempt, and a Core stage retry multiplies with a Polly retry:
`(1 + Rcore) × (1 + Rpolly)` inner attempts at most. The package README covers
the lifecycle, final-outcome, mapper, and hedging rules.

The facade references `SmartPipe.Extensions.Polly` as part of the bundle and no
longer depends on `Microsoft.Extensions.Resilience`. The `polly-direct`,
`polly-trim`, and `polly-nativeaot` consumer scenarios build, publish, and run
the decorator without the facade.

SP220-17 preserves the existing 23 forwarders and 13 facade-owned public identities,
checks each forwarder's destination and per-asset implementation, rejects new
facade public types, and adds HealthChecks/OpenTelemetry to the runtime bundle.
The [compatibility matrix](../reference/compatibility/2.1.2-to-2.2.0.md)
derives all 42 baseline identities from the immutable 2.1.2 package assets and
the existing ownership policy. All six ADR-0004 removals stay absent.

## Compatibility boundary

Retaining a namespace for source migration does not preserve assembly identity by
itself; the forwarders and wrappers described above are what carry 2.2.0 binary
compatibility, and the 2.1.2 packages are kept as immutable integrity/comparison
material for that validation. A type that a future approved removal drops
receives no forwarder or wrapper solely to load an old binary, so applications
using such an identity must update references and recompile. The HTTP and
Polly removals above are such identities. This guide does not change the selected
version.

Approved removals use the existing ownership/removal matrix. The minimal
prerequisite is `Removed` support in the validator/schema plus targeted native
ApiCompat suppression. There is no second manifest or global `NoWarn`; the
post-09 preflight removed no owner and therefore added no suppression.

## CSV lifecycle boundary

`SmartPipe.Extensions.Csv` exposes file-only strict definitions; public stream
ownership and `leaveOpen` options are not part of the migration surface. The
runtime component owns its internal CsvHelper wrapper, bounded bridge or record
writer, and file reader/stream. Cleanup releases each owned resource once,
attempts all releases in reverse acquisition order, and keeps a primary
operation failure before cleanup failures. This behavior is internal lifecycle
semantics, not a new public API.

## Dapper lifecycle boundary

`SmartPipe.Extensions.Dapper` exposes explicit-SQL definitions through
`DapperPipelineComponents` and the typed `FromQuery`/`ToCommand`/`ToBatchCommand`
builders. Composing a component or definition performs no I/O. Each run borrows a
`DbDataSource` or a caller-supplied async connection factory, opens a fresh
connection, and disposes it exactly once; on that explicit-SQL surface there is no
`leaveOpen` option, no external `DbTransaction` injection, and no shared-connection
contract. The forwarded legacy types keep their shipped `leaveOpen` constructors. The
scalar command sink performs one awaited execute per envelope, and the batch sink
treats one preformed `IReadOnlyList<T>` envelope as a single bounded parameter
sequence with an explicit `PerBatch` or `None` transaction mode. Cleanup attempts
every owned release in reverse acquisition order and keeps a primary operation
failure before cleanup and rollback failures. The legacy `DapperSelector<T>` and
`DbSink<T>` identities move into the leaf unchanged under their preserved
namespaces and stay reachable through facade type forwarding.

## PostgreSQL lifecycle boundary

`SmartPipe.Extensions.PostgreSql` is a new optional leaf rather than a moved identity: it has
no type forwarder and no required package edge from `SmartPipe.Extensions`, so installing the
bundle neither adds nor implies it. It exposes binary
`COPY … TO STDOUT (FORMAT BINARY)` as a streaming source, binary
`COPY … FROM STDIN (FORMAT BINARY)` as a batch sink, and `LISTEN`/`NOTIFY` as a notification
source, all over an application-owned `NpgsqlDataSource` that SmartPipe never constructs,
configures, mutates or disposes and never accepts as a connection string. Composing a
component or definition performs no I/O; each run opens its own connection, owns it exactly
once, and releases owned resources in reverse acquisition order while keeping a primary
operation failure ahead of cleanup failures. Every component rejects a non-null
`System.Transactions.Transaction.Current` with `InvalidOperationException` before opening a
connection and again before starting COPY or `LISTEN` protocol work, because Npgsql would
otherwise auto-enlist the connection and break the one-envelope-one-COPY contract.

One batch envelope is one complete COPY operation: a successful `WriteAsync` means
`CompleteAsync` already succeeded, a cancelled or failed import is reverted by PostgreSQL when
the importer is disposed, and an earlier completed batch stays committed if a later batch
fails. There is no retry, and a connection failure around completion leaves the outcome
unproven rather than guessed, so replaying a batch needs an application-owned idempotency
strategy. The `LISTEN` source is a best-effort wake-up signal, not a durable queue: a peer
`NOTIFY` is delivered only after commit, identical channel-and-payload notifications in one
transaction may be folded into a single delivery, `LISTEN` itself takes effect at commit, and
session termination removes the registrations with no reconnect, so notifications issued
during the gap cannot be recovered. The durable-outbox-plus-NOTIFY wake-up pattern is the
supported shape: the durable table is the truth and `NOTIFY` is only the wake-up signal, so
a missed notification costs latency rather than data.

Choose the database integration by capability rather than by provider:

| Concern | `SmartPipe.Extensions.Dapper` | `SmartPipe.Extensions.PostgreSql` |
|---|---|---|
| Provider boundary | borrowed `DbDataSource` or async connection factory | borrowed, application-owned `NpgsqlDataSource` |
| Operation shape | one awaited execute per envelope, or one bounded parameter sequence per batch | one complete binary COPY per batch envelope |
| Data path | parameters and `DbDataReader` rows | server-side binary COPY stream typed through Npgsql |
| Transaction control | explicit `PerBatch` or `None` mode; `RollbackAsync` on failure | none; an ambient `Transaction.Current` is rejected |
| Failure semantics | a commit that may have reached the server keeps an unknown outcome | a completion that may have reached the server keeps an unknown outcome; an earlier completed batch is not reverted by a later failure |
| Scope | generic across ADO.NET providers | PostgreSQL-specific statements and Npgsql typing |

| Concern | `SmartPipe.Extensions.EntityFrameworkCore` | `SmartPipe.Extensions.PostgreSql` |
|---|---|---|
| Data model | mapped entities, `IQueryable`, compiled queries | unmapped rows plus a caller-supplied COPY statement and row callbacks |
| Provider coupling | provider-neutral; no provider package reference | Npgsql/PostgreSQL-native by design |
| Per-run resource | exactly one `DbContext` from the application factory | exactly one `NpgsqlConnection` per component per run, from the borrowed data source |
| Write path | EF-tracked changes through the application's save path | binary COPY; no change tracking, no unit of work |
| Best for | ORM reads and unit-of-work consistency | bulk ingest/export and cross-session wake-up |

Composition follows the other leaves: the package has no DI, OpenTelemetry, Hosting, or Polly
dependency, so the application builds the `NpgsqlDataSource` and the definition and registers
the definition with `AddSmartPipe().AddPipeline(definition)`; database client instrumentation
stays with `Npgsql`/`Npgsql.OpenTelemetry`, and pipeline instrumentation stays with
`SmartPipe.Extensions.OpenTelemetry`. For trimming and NativeAOT, build the data source with
`NpgsqlSlimDataSourceBuilder` and keep COPY callbacks static; caller opt-ins such as
`EnableDynamicJson` keep their own warnings. See the
[PostgreSQL subsystem reference](../postgresql.md) and
[AOT and trimming compatibility](../aot-compatibility.md) for the full boundary.

Security responsibility stays with the application: the package creates no connection
strings, data sources, credentials, certificates, or tokens, and it does not rotate them.
Transport encryption without server identity verification is not authenticated TLS, so a
deployment must select the Npgsql SSL verification settings appropriate to its environment;
the disposable local servers and trust authentication used by test fixtures are never a
production configuration.

## Entity Framework Core lifecycle boundary

`SmartPipe.Extensions.EntityFrameworkCore` exposes provider-neutral query sources through
`EfCorePipelineComponents.QuerySource`/`CompiledQuerySource` and the typed
`FromQuery`/`FromCompiledQuery` builders. The package references `Microsoft.EntityFrameworkCore` and
`Microsoft.Extensions.Logging.Abstractions` only and never a provider. Composing a component or
definition performs no I/O and invokes neither the context factory nor the query factory; options are
validated and snapshotted at composition. Each run creates exactly one context, owns it, and releases
it exactly once, releasing the enumerator before the context; the caller's query factory runs once at
activation, the selected tracking operator is applied once, and the run enumerates once. The forwarded
legacy `EfCoreSelector<T>` keeps its shipped borrowed-context semantics and never disposes a
caller-owned `DbContext`.
## Mapster lifecycle boundary

`SmartPipe.Extensions.Mapster` exposes `MapsterPipelineComponents.Transform<TInput,TOutput>` and the
`MapWithMapster` builder extensions over `SmartPipe.Core` and `Mapster` only. Composition fixes the whole
configuration pipeline: one caller callback runs against a fresh working `TypeAdapterConfig`, that
configuration is cloned once into a private container, and the requested root pair is compiled once.
`TypeAdapterConfig.GlobalSettings` is never read, and a callback exception is a composition failure
rather than an item failure. Each run receives a fresh Core-owned transformer over the captured delegate,
so no run clones the configuration or recompiles the root pair; nested or `MapToTarget` pairs may compile
lazily on first mapping against the private clone.

`Clone()` isolates configuration containers and recursively clones supported `IApplyable` values, but it
is not a deep immutable snapshot: ordinary objects, delegates, closures, and custom mutable values remain
shared references, so callers must not mutate them while composition or transform execution is active.
Mapping exceptions reach Core unchanged, cancellation is observed immediately before and after the
synchronous mapper, and the package logs nothing.

The forwarded legacy `SmartPipe.Extensions.Transforms.MapsterTransform<TInput,TOutput>` keeps its shipped
behaviour, including its optional `TypeAdapterConfig` constructor and its `Permanent`
`"Mapster mapping error"` stage failure; new code uses the composition API above, where Core owns result
classification. The package makes no blanket trimming or NativeAOT claim: every runtime mapping entry
point carries `RequiresUnreferencedCode` and `RequiresDynamicCode`, a trimmed publish reports the
aggregate `IL2104` for the `Mapster` and `Mapster.Core` assemblies, and executing composition under
`TrimMode=link` fails inside `Mapster.TypeAdapterConfig.GetMapFunction`. The trimming-safe route is a
hand-written or source-generated mapper through `PipelineTransformer.FromFunc`, which the
`mapster-trim-diagnostic` consumer publishes and runs under `TrimMode=link`.

Servicing note: `Mapster` moved from the `10.0.10` baseline to the consolidated `10.0.13`
release pin. The `10.0.12` step in that servicing sequence changes two behaviours worth checking in a
consumer: a custom converter registered with `MapWith` now observes a null source member that it previously
never saw, and `IgnoreIf` now applies to record properties. The public
`TypeAdapterSetter<TInput,TOutput>.MapWith`/`MapToTargetWith` signatures gained an optional parameter, so
assemblies compiled against `10.0.10` must be recompiled. The later `10.0.13` consolidation is validated by
the current locked restore, Mapster suite and packed consumers; it does not change the migration contract above.
## Removed and moved integration surface

- DI, Hosting, and HealthChecks implementations move to their dedicated leaves.
  Under [ADR-0002](../adr/0002-smartpipe-2.2-legacy-compatibility-quarantine.md)
  their coupled legacy identity cluster stays physically in
  `SmartPipe.Extensions` for 2.2.0 as `obsolete-wrapper` quarantine, and it is a
  removal candidate for the next major release rather than an SP220-17 removal.
- SP220-10 through SP220-14 move the Dapper, EF, Mapster, HTTP, and Polly
  adapters into their leaf packages. Retained identities use `type-forward` or
  `obsolete-wrapper`; ADR-0004's HTTP identities and the no-op
  `PollyResilienceTransform<T>` instead use `Removed` and targeted native
  ApiCompat suppression, with no wrapper or forwarder.
- HTTP consumers split composite JSON/resilience usage between the transport
  and codec packages. Dapper, EF, Mapster, and Polly consumers use the current
  leaf contracts described by their package READMEs.
- SP220-15 adds `SmartPipe.Extensions.PostgreSql` as an optional new leaf for binary COPY and
  `LISTEN`/`NOTIFY` on an application-owned `NpgsqlDataSource`. Nothing moves into it: it has
  no facade forwarder and no required package edge, and the facade bundle does not reference
  it.
- SP220-16 adds `SmartPipe.Testing` with `TestActivation.Create` and bounded
  `SourceReader.ReadEnvelopesAsync`. It is published separately for test
  projects and must never become a runtime dependency.
- SP220-17 completes the remaining facade assembly: outstanding forwarders,
  moved-implementation removal, allowed compatibility wrappers only, and package
  validation before packing. It must not ship an empty runtime DLL or a
  meaningless symbol package.

## Migration steps

1. Inventory references to `SmartPipe.Extensions` and the old integration
   identities, then map each use to a leaf package and current API.
2. Add the selected leaf references, or keep the convenience bundle when its
   17 direct dependencies (18 SmartPipe IDs including itself) are intentional. Do not add `SmartPipe.Testing` to
   production package dependencies.
3. Update namespaces, constructors, builders, and signatures against the
   destination package. Treat compiler errors as migration work; do not restore
   an identity that an approved removal dropped with local wrappers or blanket
   warning suppression.
4. Rebuild direct, facade/bundle, and current-source consumers. For retained
   identities, separately run binaries compiled against 2.1.2 with the 2.2.0
   runtime packages without recompiling the consumer; its DLL SHA must remain
   unchanged. Removed HTTP identities and `PollyResilienceTransform<T>` require
   migration and recompilation. Check package metadata,
   dependency allowlists, API/removal ownership, and the applicable trim/AOT
   contract from each package README.
5. Record the candidate SHA and run the exact-head CI, security, Sonar, and
   independent-review evidence required by the governance policy. A skipped
   review or missing required gate leaves migration acceptance open.

## Upgrade and deployment checks

Target `net10.0` and update explicit SmartPipe package references together to
2.2.0. Internal SmartPipe dependencies use a minimum 2.2.0 version, without
exact or upper-bound ranges. For the minimal retained-API update:

```sh
dotnet package add SmartPipe.Extensions --version 2.2.0
dotnet restore
dotnet build -c Release
```

For a narrow JSON application, install `SmartPipe.Extensions.Json` instead of
the facade. Existing retained type namespaces stay unchanged; new canonical
APIs use their leaf-specific namespaces. The historical JSON split guide
describes the 2.1.2 release and remains unchanged.

Legacy DI/Hosting/Health signatures remain in the facade DLL. Only synchronous
factory `Start` is obsolete; the whole cluster is not newly deprecated.
Canonical DI factories use `StartAsync`, one async scope per run, and dispose
the scope after Core has disposed the run. Use the executable
[DI source consumer](../../tests/Consumers/Scenarios/dependency-injection-facade-source/Program.cs)
and [canonical DI consumer](../../tests/Consumers/Scenarios/dependency-injection-direct/Program.cs)
alongside the [hosting](2.2.0-hosting.md) and [health](2.2.0-health-checks.md) guides.
The [bundle consumer](../../tests/Consumers/Scenarios/opentelemetry-facade/Program.cs)
uses only the facade SmartPipe package reference to exercise canonical
HealthChecks and OpenTelemetry and retained hosted registration.

Source, binary and behavioral compatibility are distinct: namespace preservation
alone does not establish binary identity; successful compilation alone does not
prove lifecycle behavior. CSV strict, HTTP codec and Polly decorator contracts
are described above and in their leaf READMEs. The facade carries no blanket AOT
guarantee; install and verify only the leaves your trimmed/AOT application needs.

| Deployment symptom | Check |
|---|---|
| `TypeLoadException` for a removed HTTP/Polly type | Migrate to the listed leaf replacement and rebuild the application; no compatibility shim exists. |
| Missing retained forwarded type | Deploy both the facade DLL and its destination leaf DLL from the current package graph. |
| `MissingMethodException` or conflicting signatures | Check every resolved SmartPipe version, retained signatures and third-party dependency versions; avoid mixing old DLLs with current deployment metadata. |
| Works after build but fails in deployment | Regenerate `.deps.json`, clean stale output and verify the loaded DLL/package versions. Binary tests preserve the original consumer DLL while refreshing deployment metadata. |
| Unexpected broad dependency graph | Remove the facade reference and install specific leaves; Testing/PostgreSql are separate references. |

## Post-09 preflight boundary

The accepted CSV merge is `db8444655fa48ced526344451e758828d1793f0c`; its
focused CSV and ownership checks passed `50/50` and `6/6`. Sonar classifications
and the exact-head check map are retained as evidence, not release or remote-
Sonar completion. Servicing probes used the accepted SDK `10.0.303` pin and
current pins in disposable projects. The Mapster private-clone and
eager-root-compile correction probed here was implemented by SP220-12, which also
selected `Mapster` `10.0.12` from a disposable two-version probe and recorded the
resulting lock, API, and behaviour deltas above.

The migration guide, package READMEs, ownership/removal matrix, and consumer
checks are the recoverable record of each approved break. No release, publish,
or version change is implied by this guide.
