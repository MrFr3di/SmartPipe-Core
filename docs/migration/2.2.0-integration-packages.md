# Migrate integration packages to SmartPipe 2.2.0

This guide covers the intentional migration from the 2.1.2 broad integration
package to the 2.2.0 leaf-package layout. Read it with the constraints in
[ADR-0001](../adr/0001-smartpipe-2.2-package-boundaries.md), the [architecture
plan](../plans/2.2.0-extension-architecture.md), and the [branch/review
policy](../governance/2.2.0-branch-and-review-policy.md).

## Choose a package

New applications should reference only the leaves they use. Package references
bring `SmartPipe.Core` transitively where required.

| Scenario | Packages to reference |
|---|---|
| Pipeline registration and keyed services | `SmartPipe.Extensions.DependencyInjection` |
| Generic Host orchestration or health checks | `SmartPipe.Extensions.Hosting`, `SmartPipe.Extensions.HealthChecks` |
| Telemetry | `SmartPipe.Extensions.OpenTelemetry` |
| JSON or CSV files and framing | `SmartPipe.Extensions.Json`, `SmartPipe.Extensions.Csv` |
| HTTP transport and JSON codecs | `SmartPipe.Extensions.Http`, optionally `SmartPipe.Extensions.Http.Json` |
| Dapper, EF Core, or Mapster | `SmartPipe.Extensions.Dapper`, `SmartPipe.Extensions.EntityFrameworkCore`, or `SmartPipe.Extensions.Mapster` |
| Resilience, transforms, validation, logging, or channels | `SmartPipe.Extensions.Polly`, `SmartPipe.Extensions.Transforms`, `SmartPipe.Extensions.DataAnnotations`, `SmartPipe.Extensions.Logging`, or `SmartPipe.Extensions.Channels` |
| Reusable framework-neutral test primitives | `SmartPipe.Testing` in test projects only |

`SmartPipe.Extensions` remains available as a convenience bundle for an
application that intentionally wants the complete runtime integration set. It
contains dependency metadata only: no implementation DLL, type forwarders,
aliases, or legacy wrappers. Its release dependency closure has 17 entries:
`SmartPipe.Core` plus the 16 runtime integration leaves. `SmartPipe.Testing` is
published separately and is excluded from that runtime graph.

## Intentional compatibility boundary

The 2.2.0 migration permits source and binary breaks. The old broad facade
assembly is not retained as a compatibility implementation surface. Removed
types do not receive a forwarder or wrapper solely to load an old binary, so
applications using those identities must update references and recompile.
Retaining a namespace for source migration does not preserve assembly identity.

The project keeps the 2.1.2 packages as immutable integrity/comparison material
for approved removals. Old-binary loading is not a successful 2.2.0 consumer
gate. This approved 2.2.0 boundary does not make a normal binary-backcompat
promise and does not change the selected version.

Approved removals use the existing ownership/removal matrix. The minimal
prerequisite is `Removed` support in the validator/schema plus targeted native
ApiCompat suppression. There is no second manifest or global `NoWarn`; the
post-09 preflight removed no owner and therefore added no suppression.

## CSV lifecycle boundary

`SmartPipe.Extensions.Csv` exposes file-only strict definitions; public stream
ownership and `leaveOpen` options are not part of the migration surface. The
runtime component owns its internal CsvHelper wrapper, bounded bridge or record
writer, and file reader/stream. Cleanup releases each owned resource once,
attempts all releases in reverse acquisition order, and keeps a primary
operation failure before cleanup failures. This behavior is internal lifecycle
semantics, not a new public API.

## Removed and moved integration surface

- DI, Hosting, and HealthChecks implementations move to their dedicated leaves;
  their obsolete broad-package quarantine and compatibility identities are
  removed through the owning plans and the existing ownership/removal matrix.
- SP220-10 through SP220-14 remove obsolete Dapper, EF, Mapster, HTTP, and Polly
  adapters recorded as `Removed`; useful retained leaf contracts stay only when
  the matrix marks them retained.
- HTTP consumers split composite JSON/resilience usage between the transport
  and codec packages. Dapper, EF, Mapster, and Polly consumers use the current
  leaf contracts described by their package READMEs.
- SP220-16 completes the remaining broad-package cleanup and validates the
  dependency-only package kind before packing. It must not add `lib`, `ref`,
  `runtimes`, XML, an empty runtime DLL, or a meaningless symbol package.

## Migration steps

1. Inventory references to `SmartPipe.Extensions` and the old integration
   identities, then map each use to a leaf package and current API.
2. Add the selected leaf references, or use the dependency-only bundle when its
   full 17-dependency closure is intentional. Do not add `SmartPipe.Testing` to
   production package dependencies.
3. Update namespaces, constructors, builders, and signatures against the
   destination package. Treat compiler errors as migration work; do not restore
   removed identities with local wrappers or blanket warning suppression.
4. Rebuild direct, bundle, and current-source consumers. Check package kind,
   dependency allowlists, API/removal ownership, and the applicable trim/AOT
   contract from each package README.
5. Record the candidate SHA and run the exact-head CI, security, Sonar, and
   independent-review evidence required by the governance policy. A skipped
   review or missing required gate leaves migration acceptance open.

## Post-09 preflight boundary

The accepted CSV merge is `db8444655fa48ced526344451e758828d1793f0c`; its
focused CSV and ownership checks passed `50/50` and `6/6`. Sonar classifications
and the exact-head check map are retained as evidence, not release or remote-
Sonar completion. Servicing probes used the accepted SDK `10.0.303` pin and
current pins in disposable projects; candidate package updates were evaluated
without changing tracked package or lock files, so the pin/package decision is
deferred to the owning plan and release validation. The Mapster private-clone
and eager-root-compile correction was covered by the disposable consumer probe
before downstream sequencing.

The migration guide, package READMEs, ownership/removal matrix, and consumer
checks are the recoverable record of each approved break. No release, publish,
or version change is implied by this guide.
