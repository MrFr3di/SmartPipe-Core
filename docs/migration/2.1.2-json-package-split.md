# Migrate JSON Integrations to SmartPipe.Extensions.Json 2.1.2

SmartPipe 2.1.2 moves JSON file, transform, and JSON dead-letter integrations
from `SmartPipe.Extensions.dll` to the dedicated
`SmartPipe.Extensions.Json.dll` assembly.

## Before

```xml
<PackageReference Include="SmartPipe.Extensions" Version="2.1.1" />
```

## Recommended

```xml
<PackageReference Include="SmartPipe.Core" Version="2.1.2" />
<PackageReference Include="SmartPipe.Extensions.Json" Version="2.1.2" />
```

No `using` directive changes are required. The existing namespaces under
`SmartPipe.Extensions.Selectors`, `SmartPipe.Extensions.Sinks`, and
`SmartPipe.Extensions.Transforms` are preserved.

## Compatibility

`SmartPipe.Extensions` 2.1.2 depends transitively on
`SmartPipe.Extensions.Json` and forwards the moved types. Existing source code
and binaries compiled against `SmartPipe.Extensions` 2.1.1 therefore do not
require an immediate source change.

The forwarded surface includes:

- `JsonFileSource<T>` and `DeadLetterSource<T>`;
- `JsonFileSink<T>` and `DeadLetterSink<T>`;
- `DeadLetterWriteFailureMode` and `DeadLetterWriteException`;
- `JsonTransform<TInput,TOutput>`.

The compatibility dependency and forwarders remain throughout SmartPipe 2.x.
Direct references are recommended for a minimal dependency graph. The 2.x
compatibility bridge has no scheduled removal release.

## Why reference the package directly

- JSON-only applications avoid Dapper, EF Core, Mapster, CsvHelper, HTTP,
  resilience, hosting, and health-check dependencies.
- Package ownership is explicit.
- Trimming and NativeAOT guidance is scoped to the JSON assembly.

`JsonLinesDeadLetterSerializer<T>` is not moved; it remains part of
`SmartPipe.Core`.

## Trimming and NativeAOT

Use constructors that accept source-generated `JsonTypeInfo<T>` metadata.
Reflection-based constructors remain available but carry
`RequiresUnreferencedCode` and `RequiresDynamicCode` annotations.

## File format compatibility

`JsonFileSink<T>` continues to write one JSON array for every flushed batch,
followed by a newline. Multiple batches are batch JSON Lines: they are not
conventional one-object-per-line NDJSON and do not form one root JSON array.

Options-based constructors can explicitly select `Array`, `Ndjson`, or
`BatchJsonLines`. `JsonFileSource<T>` can auto-detect non-collection payloads;
collection-valued payloads must specify the format. Reads are strict by default,
and `SkipAndLog` requires an `ILogger`.
