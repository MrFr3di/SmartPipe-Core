# Migrating Hosting to 2.2

SmartPipe 2.2 introduces the canonical `SmartPipe.Extensions.Hosting` package.
The 2.1 Hosting API remains in `SmartPipe.Extensions` for source and binary
compatibility, but it is not redirected to the new lifecycle model.

## Package references

New applications reference the DI and Hosting leaves directly:

```xml
<PackageReference Include="SmartPipe.Extensions.DependencyInjection" Version="2.2.0" />
<PackageReference Include="SmartPipe.Extensions.Hosting" Version="2.2.0" />
```

`SmartPipe.Extensions.Hosting` does not bring in HealthChecks or the broad
`SmartPipe.Extensions` façade.

## Registration

Replace a legacy registration:

```csharp
services.AddSmartPipeHostedService<Order, OrderDto>(
    "orders",
    pipeline => pipeline
        .UseSource<OrderSource>()
        .UseStage<OrderStage>()
        .UseSink<OrderSink>());
```

with a canonical DI definition and explicit Hosting opt-in:

```csharp
var smartPipe = services.AddSmartPipe();
smartPipe.AddPipeline(ordersDefinition)
    .RunAsHostedService(options =>
    {
        options.Order = 0;
        options.DrainTimeout = TimeSpan.FromSeconds(30);
        options.FailureBehavior =
            SmartPipeHostedPipelineFailureBehavior.StopApplication;
        options.CompletionBehavior =
            SmartPipeHostedCompletionBehavior.KeepHostAlive;
    });
```

Use a unique `PipelineKey` for every hosted registration. Input/output types do
not form the hosted identity. All canonical registrations share one orchestrator,
start sequentially, and stop in reverse order; Generic Host concurrent-service
options do not change that internal ordering.

## Behavior changes to choose explicitly

- Startup failure rolls back every earlier run in reverse order.
- Shutdown attempts bounded drain; timeout, cancellation, or drain fault aborts
  the run before disposal.
- Finite completion keeps the host alive by default and never restarts the run.
- `Rethrow` delegates the final host action to
  `HostOptions.BackgroundServiceExceptionBehavior`.
- `StopApplication`, `MarkUnhealthyAndKeepHostAlive`, and `Ignore` apply per
  pipeline rather than through one global legacy option.

Applications that must preserve exact 2.1 descriptor shape, generic-pair
identity, or hosted-service behavior should keep the legacy API for the 2.x line
and migrate only after accepting these canonical lifecycle semantics.
