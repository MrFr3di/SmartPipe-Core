# SmartPipe.Core 1.0 to 1.1 Migration Guide

SmartPipe.Core 1.1.0 is a compatibility-preserving release. Existing
`ISource<T>`, `ITransformer<TInput,TOutput>`, `ISink<T>` and
`SmartPipeChannel<TInput,TOutput>` consumers remain supported.

## API Direction

For new code, prefer `PipelineBuilder` and the envelope-aware `IPipeline*`
interfaces:

- `IPipelineSource<T>`
- `IPipelineTransformer<TInput,TOutput>`
- `IPipelineSink<T>`

The legacy interfaces remain stable for 1.x consumers and are bridged through:

- `LegacySourceAdapter<T>`
- `LegacyTransformerAdapter<TInput,TOutput>`
- `LegacySinkAdapter<T>`

Use the new interfaces when a component needs original payload preservation,
metadata ownership, lineage, retry/dead-letter context, or observer events.

Envelope-aware typed pipelines return a `PipelineRun<TOutput>`:

```csharp
var run = PipelineBuilder
    .From(source)
    .Transform(firstStage)
    .Transform(secondStage)
    .To(sink);

await foreach (var output in run.Outputs.ReadAllAsync())
{
    // output.Result is the compatibility result.
    // output.Envelope carries trace, metadata, lineage, and attempt metadata.
}

await run.Completion;
```

Existing legacy components can participate in this model through adapters:

```csharp
var run = PipelineBuilder
    .From(new LegacySourceAdapter<Order>(legacySource))
    .Transform(new LegacyTransformerAdapter<Order, OrderDto>(legacyTransform))
    .To(new LegacySinkAdapter<OrderDto>(legacySink));
```

## Reusable Factory Definitions

Concrete component instances are single-use by default because sources and sinks
often own enumerators, file handles, database readers, or other mutable state.
Use factories when the same declarative pipeline should create multiple runs:

```csharp
var builder = PipelineBuilder
    .FromFactory(_ => new OrderSource())
    .TransformFactory(_ => new NormalizeOrderStage())
    .TransformFactory(_ => new OrderDtoStage());

var firstRun = builder.Run();
var secondRun = builder.Run();
```

`FromFactory`, `TransformFactory`, and `ToFactory` create fresh runtime-owned
components for each run. If you pass an externally-owned singleton component,
implement `IPipelineComponentDescriptor` and declare
`PipelineComponentLifetime.SingletonExternal`; the runtime does not dispose
external singleton components by default.

## Observers

Envelope-aware typed pipelines can emit structured events:

```csharp
var run = PipelineBuilder
    .From(source)
    .Transform(stage)
    .WithObserver(observer)
    .Run();
```

Use `BestEffort` observers for logging and metrics, `Reliable` observers for
audit trails, and `Critical` observers only when an observer failure should stop
the run. In 1.1.0 observer dispatch is inline: slow observers can slow the
pipeline, and critical observer failures fault `PipelineRun<T>.Completion`.
Buffered observer dispatch is intentionally left as a later hardening step.

The 1.1.0 typed runtime emits structured run, stage, sink, and observer failure
events. Stage exceptions and sink exceptions fault `PipelineRun<T>.Completion`;
terminal fault/cancel events are best-effort diagnostics and do not replace the
original completion outcome.

## SmartPipeChannel

`SmartPipeChannel<TInput,TOutput>` remains public for compatibility and advanced
single-stage usage. Same-type transformers added to the direct channel are now
executed in insertion order. If a direct channel transformer changes the payload
type, use a typed `PipelineBuilder` flow instead of adding it to the same direct
channel.

## RunInBackground

`RunInBackground` now returns a reader connected to the running pipeline output.
The compatibility reader exposes `ProcessingResult<TOutput>` values. New runtime
APIs should prefer `PipelineRun<TOutput>.Outputs`, whose primary stream is
`PipelineOutput<TOutput>`.

## Metadata And Lineage

New envelope-aware APIs use immutable-style `MetadataBag` instead of exposing a
mutable metadata dictionary. Full lineage is opt-in because per-item lineage can
be expensive at high throughput.

## Dead Letter

1.1.0 introduces `DeadLetterEnvelope<T>`, `IDeadLetterSerializer<T>`, and
`IDeadLetterRedactor<T>` for replay-safe dead-letter designs. Existing
`DeadLetterSink<T>` behavior remains available, but replay safety depends on the
new envelope model and serializer/redactor choices.

Typed stage failures can now opt into replay-safe dead-letter persistence:

```csharp
await using var stream = File.Open("orders.dlq.ndjson", FileMode.Append);

var run = PipelineBuilder
    .From(source)
    .Transform(
        validator,
        new StageFailureOptions { OnPermanentFailure = FailureAction.DeadLetter },
        new StageDeadLetterOptions<Order>(stream))
    .Run();
```

The dead-letter payload type is the input type of the failing stage. The runtime
leaves the stream open and emits `DeadLetterWrittenEvent` after a successful
write.

Typed stage policies also support `Skip`, `StopPipeline`, and `FaultPipeline`.
Use `Skip` for invalid records that should not produce output, `StopPipeline`
when a terminal data condition should end the run cleanly, and `FaultPipeline`
when the failure should surface as `PipelineFailureActionException` through
`PipelineRun<T>.Completion`.

Typed transformer stages can also configure an attempt timeout:

```csharp
var run = PipelineBuilder
    .From(source)
    .Transform(
        transformer,
        new StageFailureOptions
        {
            Timeout = new TimeoutPolicy
            {
                AttemptTimeout = TimeSpan.FromSeconds(5),
            },
        })
    .Run();
```

When the attempt timeout expires, the typed runtime emits a failed output with a
`Timeout` error category and a `StageFailedEvent`. The terminal failure then
uses the same policy path as other stage failures.

`StageTimeout` can be used when the stage should have one overall attempt budget
even if `AttemptTimeout` is not set. In 1.1.0 it bounds typed transformer
attempt execution; full retry-delay budget enforcement remains a later
hardening item.

Typed transformer stages can retry transient failures:

```csharp
var run = PipelineBuilder
    .From(source)
    .Transform(
        transformer,
        new StageFailureOptions
        {
            Retry = new RetryPolicy(maxRetries: 3, delay: TimeSpan.FromMilliseconds(100)),
            OnRetryExhausted = FailureAction.DeadLetter,
        },
        deadLetterOptions)
    .Run();
```

Retries apply only to errors accepted by `RetryPolicy.ShouldRetry`. The runtime
updates the envelope attempt count for each retry and emits
`RetryScheduledEvent`, `RetryAttemptedEvent`, and `RetryExhaustedEvent` for
observer-based diagnostics.

## Claims

The 1.1.0 documentation avoids claims such as `0 allocations`, `0 dependencies`,
`production-ready`, exact coverage, AOT-ready, and dead-letter replay unless a CI
artifact, benchmark, package validation result, or consumer harness proves the
claim.
