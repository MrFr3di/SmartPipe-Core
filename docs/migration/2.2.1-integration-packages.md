# Upgrade SmartPipe 2.2.0 to 2.2.1

SmartPipe 2.2.1 is a PATCH servicing line over the published 2.2.0 package set.
There is no intentional package split, namespace move, or public API removal in
this servicing scope.

## Package updates

Update explicit SmartPipe package references together so the synchronized
package graph remains on one version. Keep using the narrow integration
packages preferred by 2.2.0; the broad `SmartPipe.Extensions` package remains a
compatibility facade rather than the recommended dependency for new code.

## New opt-in Core runtime policies

Applications upgrading from 2.2.0 are **not** required to enable any new
policy. Existing constructors, default retry behavior and exact sampling
continue to work unchanged.

| Optional setting | New 2.2.1 behavior | Upgrade caution |
| --- | --- | --- |
| `PipelineRuntimeOptions.RetryBudget` | Shared retry tokens per run, replenished at the configured rate. | Initial attempts do not consume retry tokens; a zero refill rate is a fixed budget. |
| `RetryPolicy.Jitter = RetryJitterMode.Full` | Randomize each runtime retry delay between zero (inclusive) and the capped computed delay (exclusive). | `RetryPolicy.GetDelay` remains deterministic; `None` stays the default. |
| `PipelineRuntimeOptions.TimedAttemptAdmission` | Cap active plus detached timed executions per run, using `TimedAttemptAdmissionMode.Wait` or `Reject`. | `Wait` observes the remaining stage deadline; `Reject` produces a permanent admission failure. Detached execution keeps its slot until observation/cleanup, even after its timeout result. |
| `CircuitBreakerPolicy.SamplingMode` / `CircuitBreakerOptions.SamplingMode` | Opt into `CircuitBreakerSamplingMode.Bucketed`, with `SamplingBucketCount` (default 64). | Exact is unchanged by default. Buckets cap retained sample storage but may include one oldest partially expired bucket; do **not** assume a bound on failure-ratio error or identical opening decisions. |

The internal processing supervisor and suppressed-output/observer gates
need no source changes from callers. Sink writes, metric recording and
Activity tracing still occur when a success output record is suppressed.
Time-bounded stages cannot forcibly terminate user operations that ignore
cancellation; consider this before choosing admission capacity.

For measurements and limitations, consult the
[runtime I/O report](https://github.com/MrFr3di/SmartPipe-Core/blob/main/benchmarks/SmartPipe.Benchmarks/RuntimeIo-results.md)
and [sampling report](https://github.com/MrFr3di/SmartPipe-Core/blob/main/benchmarks/SmartPipe.Benchmarks/CircuitBreakerSampling-results.md).

## Behavioral hardening

The legacy `DapperSelector<T>` completion log no longer writes raw SQL text at
Information level. Applications that parsed the SQL value from that log entry
should instead instrument SQL explicitly at an application-controlled boundary.

No change is made to the obsolete synchronous
`SmartPipeFactory<TInput,TOutput>.Start()` compatibility bridge in this
servicing slice; `StartAsync` remains the canonical API.

## Compatibility evidence

The published 2.2.0 packages are the immediate Package Validation baseline for
2.2.1. The immutable 2.1.2 evidence is retained only for the historical
2.1.2 → 2.2.0 migration.

See the [2.2.0 → 2.2.1 compatibility note](../reference/compatibility/2.2.0-to-2.2.1.md)
and [2.2.1 servicing notes](../releases/2.2.1.md).
