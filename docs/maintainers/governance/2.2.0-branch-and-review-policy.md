# SmartPipe 2.2.0 branch and review policy

This policy governs every SP220 EPIC and pull request targeting the 2.2.0 release. The architecture decisions are normative in [ADR-0001](../../adr/0001-smartpipe-2.2-package-boundaries.md); the [master architecture plan](../2.2.0/plans/architecture-plan.md) defines the release scope, and the [SP220-00 detailed plan](../2.2.0/plans/SP220-00-governance-and-baseline.md) defines baseline evidence.

SmartPipe is maintained by a single human maintainer. Governance therefore does
not require an unavailable independent reviewer. Safety comes from reviewable
pull requests, exact-head automated checks, immutable release evidence, protected
history, and an explicit maintainer release decision. Self-review is permitted,
but it is not described as independent assurance.

## Baseline and branch graph

The exact reviewed baseline is `8e79902d22de714f493582946f7c260462b0895e`.

```text
main
  └── release/2.2.0
        └── accepted checkpoint
              └── active checkpoint integration branch
                    └── task branches
```

- `release/2.2.0` is the protected integration branch.
- Task branches start from and target the active checkpoint integration branch.
  If it does not exist, create the local integration ref from the preceding
  accepted checkpoint before opening the first task branch; publish it when
  ready for review, without assuming a remote ref already exists.
- Each checkpoint starts from the immediately preceding accepted checkpoint. Its
  completed integration branch is promoted to `release/2.2.0` by a reviewable
  checkpoint pull request; task pull requests do not target the release branch.
- The final release pull request targets `main` from `release/2.2.0` after full release validation.
- Direct pushes, force pushes, rebases, history rewrites, and deletion of `release/2.2.0` are prohibited.
- A task branch is deleted after merge.
- Use a harness-managed worktree when provided. If repository-local worktree roots are not ignored, use an external worktree under `C:\tmp`; do not change `main` merely to enable local worktrees.

## Exact-head CI evidence

Baseline and release-candidate evidence must identify the exact candidate
commit. Dispatch CI against a branch or supported workflow ref that points to
the candidate SHA, obtain the resulting workflow run, and accept it only when
the returned `headSha` exactly equals the candidate SHA. A successful run for
an ancestor, another ref, or an earlier branch head is not evidence. Record the
candidate SHA, run ID, URL, event, status/conclusion, SDK, and every required
check in the baseline or release report.

## Branch ruleset

The repository owner applies and verifies an active GitHub ruleset (or the
closest equivalent branch-protection rule when rulesets are unavailable):

| Setting | Required value |
|---|---|
| Target | Exact match `release/2.2.0` |
| Restrict deletions | Enabled |
| Block force pushes | Enabled |
| Require pull request | Enabled |
| Required approvals | `0` for the solo-maintainer repository |
| Dismiss stale approvals on push | Disabled; there is no independent approval to refresh |
| Require approval of most recent push | Disabled; this setting explicitly requires someone other than the last pusher |
| Code-owner/required-team approval | Disabled unless the repository gains another qualified human maintainer |
| Conversation resolution | Required |
| Status checks | Required |
| Branch currentness | Required, or enforced by merge queue |
| Checks | `validation / build-test-pack`, Windows JSON lane, CodeQL, Dependency Review, baseline contract |
| Linear history | Disabled while merge commits are required for reviewed hotfix synchronization |
| Bypass | Prefer none for the normal path; any retained owner bypass is administrative recovery capability only and must not replace required machine gates |

A zero human-approval count is intentional. `require_last_push_approval` and
stale-approval dismissal are also disabled: GitHub defines last-push approval as
an approval from someone other than the last pusher, which is impossible in the
current solo-maintainer model. Requiring any of these human gates would turn
owner bypass into the routine path. That is weaker governance than requiring the
machine/security gates directly.

Ruleset application is an owner/admin gate. Do not report it complete without
recording the ruleset name, numeric ID, target, enforcement status, required
checks, bypass actors, and verification date. Missing or inactive protection
keeps the pull request non-mergeable.

## Pull request targets and merge strategy

- Every SP220 task/EPIC pull request targets the active checkpoint integration branch; it must not target `release/2.2.0` or `main` directly.
- A completed checkpoint is promoted to `release/2.2.0` through a reviewable true merge or repository-configured merge-queue result. Squash/rebase must not erase evidence required by an approved EPIC plan.
- After the first merged EPIC, `release/2.2.0` is never rebased or force-updated.
- A hotfix first merged to `main` is synchronized into `release/2.2.0` by an explicit merge commit after conflict, compatibility, and validation review. Never cherry-pick or silently replay it without documenting why the branches differ.

The 2.2.0 checkpoint sequence is E = SP220-09–12, F = SP220-13–16, and G =
SP220-17–18. F starts from accepted E; do not promote E a second time. If no F
integration ref exists, create local F from accepted E before opening its first
task branch. No remote F ref was advertised at F entry. G starts from accepted F.

## Review responsibility

The maintainer performs explicit diff review for every pull request. Review
focus depends on the changed surface:

| Change surface | Review focus |
|---|---|
| Core runtime, async lifecycle, cancellation, ownership | Runtime semantics, races, cancellation and ownership |
| Public API, namespaces, forwarding, package boundaries | Source/binary compatibility, package identity and migration |
| Workflows, repository checks, release, credentials, dependency policy | Least privilege, provenance, immutable artifacts, fail-closed behavior |
| DI, Hosting, telemetry, transport, or data integration | Framework lifecycle and integration-specific contracts |
| User-facing contract or migration guidance | Accuracy against executable compatibility evidence |

One maintainer may cover all applicable categories. Self-review is a normal
repository activity, but automated checks and exact-head evidence remain
separate controls and cannot be replaced by a review comment.

## Commit naming and scope

Prefer one reviewable commit per task or a small ordered TDD sequence. Allowed
prefixes for SP220-00 are `docs:`, `chore(governance):`,
`build(baseline):`, `test(baseline):`, and `ci(baseline):`; later EPICs
use the repository's conventional prefixes with an explicit scope. Messages
such as `update`, `misc`, or `fix stuff` are prohibited. Do not mix
governance, runtime refactoring, package movement, and unrelated cleanup. A
changed pull-request head requires fresh exact-head validation.

## Generated files and artifacts

- Never commit `.nupkg`, `.snupkg`, `artifacts/`, build output, temporary worktrees, credentials, or machine-specific paths.
- Commit a generated source, manifest, schema, snapshot, or API baseline only when its owning plan names it, generation is deterministic, and the pull request includes the generator/input and validation evidence.
- Review generated diffs for unexpected API, dependency, identity, path, timestamp, or ordering drift. Canonical hashes must exclude environment-sensitive data.

## Administrative bypass and recovery

Normal development and release promotion must not rely on an owner bypass.
Where GitHub account/repository administration retains a bypass capability for
recovery, using it is exceptional and auditable.

A bypass never permits force-pushing or deleting `release/2.2.0`, suppressing
evidence, claiming a skipped check passed, or publishing artifacts that did not
pass the release workflow. If a bypass is actually used, record actor, time,
ruleset/rule, reason, exact commits/checks affected, compensating validation,
and follow-up.

## Definition of ready, review, and done for every EPIC

These gates apply to each SP220 EPIC in addition to its detailed plan.

### Ready

- Scope, non-goals, dependencies, baseline commit, affected files/projects, and compatibility constraints are explicit with no unresolved TBDs.
- Applicable review focus and CI/consumer gates are identified.
- The task branch starts from the active checkpoint integration branch in an isolated worktree and is clean.
- Existing runtime/API behavior is located in source and tests; the smallest deterministic validation path is known.

### Review

- The task pull request targets its checkpoint integration branch and contains only the EPIC scope; the completed checkpoint pull request targets `release/2.2.0`. Both link the plan/ADR and explain compatibility, package-graph, AOT/trimming, security, and lifecycle effects as applicable.
- The maintainer reviews the current head; all conversations are resolved.
- Required checks attach to the exact pull-request head and pass. Generated files, public API changes, dependencies, and type movement receive explicit diff review.
- Deviations from architecture MUST/MUST NOT rules have an accepted superseding ADR rather than an undocumented exception.

### Done

- The task merges into its checkpoint without rewriting history and its task branch is removed; the accepted checkpoint is then merged into `release/2.2.0` through the configured strategy.
- The EPIC acceptance tests and proportional validation ladder pass; evidence is linked and exact-head where required.
- Public docs, API baselines, package allowlists, migration/consumer tests, and release records are updated when the EPIC changes their contract.
- Deferred work has a tracked owner and target; no hidden TODO/TBD or unreviewed generated/binary artifact remains.

## Policy changes

Policy changes use a dedicated governance/release pull request into the active
checkpoint unless an approved plan explicitly scopes them into another release
task. They do not require a nonexistent independent reviewer, but they do
require the same exact-head machine/security checks as other changes.
Architecture changes follow ADR-0001's supersession policy.
