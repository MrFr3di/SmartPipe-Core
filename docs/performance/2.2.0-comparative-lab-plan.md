# SmartPipe.Core 2.2.0 — Comparative Performance & Stress Lab

**Status:** experimental plan on `perf/2.2.0-comparative-lab`  
**Prepared:** 2026-09-21  
**Purpose:** obtain reproducible evidence for the full SmartPipe 2.2.0 architecture through SP220-12 against the published 2.1.2 baseline.

The comparison must be anchored to immutable revisions, not moving branch names.

| Role | Ref / SHA | State |
|---|---|---|

The product under test is never identified by the lab branch HEAD. The lab branch contains the experiment harness. Product targets are immutable SHAs/package hashes.

# 1. Research question

The lab must answer five separate questions instead of collapsing everything into one “faster/slower” number:

1. **Core efficiency:** did equivalent pipeline workloads become faster or cheaper in allocations/GC?
2. **Scalability:** did throughput, backpressure behaviour and concurrent-run capacity improve or regress?
3. **Lifecycle robustness under load:** do start/drain/abort/dispose/cancellation/failure paths remain bounded and leak-free?
4. **Integration efficiency:** what did SP220-03…12 change for DI, Hosting, HealthChecks, telemetry, Channels/Transforms/Logging/DataAnnotations, JSON, CSV, Dapper, EF Core and Mapster?
5. **Trade-offs:** where 2.2.0 intentionally pays startup/configuration cost for stronger isolation, ownership, safety, package boundaries or predictable cleanup, is the cost measured and justified?

A “win” is not defined only by lower mean latency. The report must show throughput, latency distribution where meaningful, allocation rate, GC, memory retention, ThreadPool behaviour, correctness and resource lifetime.

# 2. Experimental classes

Every scenario is classified before implementation.

## A. Strict A/B comparable

Same externally observable workload can be expressed against both 2.1.2 and 2.2.0 without changing semantics.

Examples:
- Core source → transform(s) → sink throughput;
- bounded channel/backpressure behaviour;
- legacy-compatible JSON/CSV paths;
- legacy Dapper selector / DB sink equivalents;
- legacy EF selector equivalents;
- legacy Mapster transform equivalent once SP220-12 exists;
- logging disabled/enabled paths where semantics match.

These scenarios may report:
- 2.2.0 / 2.1.2 ratio;
- percentage change;
- allocation delta;
- statistically supported regression/improvement.

## B. Semantically comparable, API-different

The workload goal is the same but the canonical 2.2.0 API is different.

Examples:
- 2.1.2 immediate builder/start versus 2.2.0 reusable immutable definition;
- legacy connection/context ownership versus run-owned factory model;
- old broad integration versus 2.2.0 leaf package canonical path.

These may report side-by-side numbers, but the report must explicitly label them **evolution comparisons**, not pure micro-regressions.

## C. 2.2.0-only characterization

No honest 2.1.2 equivalent exists.

Examples:
- cached generic definition compilation;
- reusable concurrent definitions;
- keyed DI registry/provider;
- multi-run keyed health observation;
- strict CSV bounded framing;
- Mapster isolated private configuration template;
- package-specific AOT/trim behaviour.

These receive absolute measurements and scaling curves only. No invented “% faster than 2.1.2”.

# 4. Environment contract

Primary comparisons are valid only when both targets run under the same environment contract.

Record for every run:

- OS + version/build;
- architecture;
- CPU model, logical/physical core count;
- RAM;
- .NET SDK and runtime versions;
- BenchmarkDotNet version;
- power profile;
- virtualization/container state;
- GC mode;
- processor affinity if used;
- repository/harness SHA;
- baseline and candidate SHAs;
- package hashes;
- process environment relevant to .NET/JIT/GC;
- UTC timestamp;
- run order.

The current repository pins SDK `10.0.303`; the lab should keep the runner/toolchain fixed for the primary comparison unless an explicit toolchain experiment says otherwise.

## 4.1 Run-order bias

Do not run all baseline measurements first and candidate measurements hours later.

Preferred full-run order:

```text
A1 → B1 → B2 → A2
A3 → B3 → B4 → A4
```

or another fixed counter-balanced schedule.

This reduces bias from thermal state, background activity and machine drift.

## 4.2 GitHub-hosted runners

GitHub-hosted runners are useful for:
- compilation;
- benchmark discovery;
- BenchmarkDotNet Dry/Short smoke;
- correctness prechecks;
- fixed-work stress correctness;
- leak/lifecycle invariants;
- artifact/schema validation.

They are **not authoritative for hard wall-clock regression gates** because the underlying hardware/noise is not controlled.

Authoritative performance ratios require a controlled reference machine or dedicated self-hosted runner.

# 5. Measurement layers

## Layer 1 — BenchmarkDotNet micro/meso

Purpose: isolated CPU/allocation/startup/hot-path measurements.

Required:
- Release;
- separate benchmark processes;
- warmup/pilot handled by BenchmarkDotNet;
- `MemoryDiagnoser`;
- `ThreadingDiagnoser` only on scenarios where it adds signal;
- correctness precheck outside the measured operation;
- raw BenchmarkDotNet JSON/CSV/Markdown artifacts retained;
- no manually added inner loop merely to “make timings larger” unless the benchmark is explicitly a batch operation.

Main statistics:
- mean;
- median;
- error/confidence information from BDN;
- ratio where valid;
- allocated bytes/op;
- Gen0/Gen1/Gen2;
- completed work items / lock contention for selected concurrent scenarios.

## Layer 2 — deterministic stress

Purpose: find saturation, races, unbounded queues, cleanup bugs and concurrency degradation.

Stress is expressed primarily in **work units**, not “sleep for N seconds”:
- exact item counts;
- exact concurrent run counts;
- deterministic failure schedule;
- deterministic cancellation point;
- deterministic seeds where randomized chunking is useful.

Collect:
- completed items;
- failed/filtered/dropped items;
- total elapsed time;
- items/s;
- peak/current queue depth where available;
- allocation/GC counters;
- working set;
- ThreadPool thread count and queue length;
- exceptions;
- SmartPipe metrics required to prove workload equivalence.

## Layer 3 — soak/leak

Purpose: detect retention and long-lived degradation that microbenchmarks cannot see.

Profiles:
- 30 min developer smoke;
- 60 min standard lab;
- 120 min extended/nightly.

Check:
- managed heap trend after warmup;
- working-set trend;
- Gen2 frequency;
- thread count;
- ThreadPool queue;
- handle/fd trend;
- active run count;
- connection/context/resource return;
- error/drop/retry counters;
- final full cleanup.

Use `dotnet-gcdump` only at selected checkpoints because collection triggers a full GC and would contaminate the performance interval.

## Layer 4 — process/application scenarios

Optional second stage using Microsoft.Crank for stable application-level orchestration:
- Generic Host startup/run/shutdown;
- telemetry-enabled host;
- later HTTP scenarios.

Crank is not required for the first implementation because SmartPipe is primarily an in-process library; BenchmarkDotNet + deterministic stress are the primary tools.

# 6. Scenario matrix for SP220-01…12

## SP220-01 — package/infrastructure

Mostly non-runtime. Measure separately from hot-path claims:

- restore/package closure size;
- package count/direct dependency closure;
- build/pack time as engineering metrics;
- cold application load/start footprint for direct leaf consumer versus broad facade;
- loaded assembly count for representative minimal consumers.

Do not claim package split makes the pipeline runtime faster unless runtime measurements prove it.

## SP220-02 — Core definition model

Benchmark:
- build definition: 0 / 1 / 10 stages;
- first compile: 0 / 1 / 10 stages;
- cached compile;
- first StartAsync;
- repeated StartAsync on reusable definition;
- single-item and 1k/100k/1M item flow;
- stage counts 0 / 1 / 5 / 10;
- allocation/item;
- run creation/disposal cost.

Stress:
- 32 reusable-definition concurrent runs;
- 1000 sequential runs;
- concurrent dispose;
- activation failure + rollback;
- cancellation at source/stage/sink boundaries.

Compare legacy-compatible workload against 2.1.2 separately from new-definition characterization.

## SP220-03 — Dependency Injection

Benchmark:
- AddSmartPipe registration;
- AddPipeline registration;
- keyed factory lookup;
- StartAsync scope creation/readiness;
- terminal unregister + scope disposal.

Stress:
- many keys;
- same generic type pair with many keys;
- 32 parallel runs;
- scoped component creation/disposal;
- start failure cleanup.

Metrics: startup overhead and allocations; no artificial service-resolution loops that do not represent real runs.

## SP220-04 — Hosting

Meso/process scenarios:
- 1 / 8 / 32 hosted pipelines;
- sequential startup;
- reverse stop;
- drain success;
- drain timeout → abort;
- partial-start rollback;
- pipeline fault monitoring.

Primary outputs:
- host-to-ready latency;
- stop latency;
- cleanup completion;
- leaked runs/scopes = 0.

No hard timing gate on GitHub-hosted runners.

## SP220-05 — HealthChecks

Benchmark:
- liveness evaluation;
- readiness evaluation;
- aggregate readiness over 1 / 8 / 32 keys;
- observation snapshot publication.

Stress:
- concurrent run updates + health reads;
- 32 active runs/key where supported;
- terminal snapshot replacement.

Report lookup/evaluation allocations and contention separately from Core hot path.

## SP220-06 — OpenTelemetry

Four conditions:
1. instrumentation package not registered;
2. registered, no exporter/listener consuming;
3. in-memory metrics/traces enabled;
4. representative OTLP exporter setup in process scenario.

Measure:
- overhead/item;
- allocations/item;
- activity creation rate;
- metric recording cost;
- effect on throughput.

The lab must not blame SmartPipe for exporter/network cost without separating exporter-enabled results.

## SP220-07 — Channels / Transforms / Logging / DataAnnotations

Channels:
- 1/2/N readers;
- bounded capacities 1 / 32 / 1024;
- fast producer/consumer;
- producer faster than consumer;
- cancellation while output is blocked.

Transforms:
- conditional/filter/composite;
- 1/5/10 transform chains;
- allocation/item.

Logging:
- log disabled;
- enabled with no payload formatter;
- formatter path;
- bounded payload formatting.

DataAnnotations:
- legacy reflection path;
- AOT-safe rule path;
- valid/invalid mix.

## SP220-08 — JSON

Benchmark:
- JSON array streaming;
- NDJSON;
- 1 / 1k / 100k records;
- source-generated metadata path;
- sink;
- dead-letter framing where comparable.

Stress:
- random deterministic chunk sizes;
- split UTF-8;
- oversized record handling;
- early break;
- cancellation while framing;
- 32 concurrent runs.

Use memory-backed streams for parser throughput. File-backed scenarios are separate and not hard cross-OS latency gates.

## SP220-09 — CSV

Required matrix from the design is preserved:
- legacy source 100k;
- strict source 100k;
- quoted multiline;
- oversized skip path;
- legacy sink 100k;
- strict sink 100k;
- allocation/record;
- definition compile/start separate from I/O.

Additional stress:
- 32 concurrent sources/sinks;
- random deterministic chunking;
- cancellation in framing states;
- cleanup/rollback failure paths.

## SP220-10 — Dapper

Use SQLite/in-process provider for reproducible local integration and provider fakes for lifecycle paths.

Benchmark:
- source 1 / 1k / 100k rows;
- default mapper;
- explicit mapper;
- sink batch=1;
- sink batch=100;
- transaction none/per-batch;
- definition/start overhead.

Stress:
- 100k streaming rows with bounded memory;
- 100k writes;
- 32 concurrent definitions;
- cancellation/early break;
- transaction rollback and cleanup.

Provider/network latency is informational. Hard gates focus on allocation shape, boundedness and lifecycle.

## SP220-11 — Entity Framework Core

Benchmark:
- 1 / 100 / 10k rows;
- NoTracking / identity-resolution / Tracking;
- pooled vs regular context factory;
- queryable vs compiled query;
- early break at 1 / 100.

Stress:
- 1000 sequential runs;
- 32 concurrent runs × 100 iterations;
- distinct context identity;
- no cross-run query reuse;
- context/entity collection checks.

Document provider buffering separately; do not claim provider-wide constant memory.

## SP220-12 — Mapster

This matrix is planned from the SP220-12 specification and becomes executable only after the implementation SHA exists.

Benchmark:
- configuration/template creation;
- cold compile;
- first item after InitializeAsync;
- steady-state flat mapping;
- nested/collection mapping;
- 100k mappings;
- allocations.

Stress:
- 32-run isolation;
- no GlobalSettings coupling;
- no lazy compile leaking into first steady-state item;
- deterministic behaviour under test-order repetition.

Compare the legacy `MapsterTransform<TInput,TOutput>` path against 2.1.2 only where semantics match. Treat the isolated canonical path as a 2.2.0 evolution/characterization scenario.

# 7. Backpressure and saturation profiles

Core stress profiles:

| Profile | Producers | Consumers | Capacity | Goal |
|---|---:|---:|---:|---|
| SPSC-small | 1 | 1 | 1 | maximum backpressure pressure |
| SPSC-normal | 1 | 1 | 256 | steady throughput |
| MPSC | 8 | 1 | 256 | contention |
| MPMC | 8 | 8 | 1024 | scheduler/coordination |
| Slow sink | fast | 1 | 32 | bounded waiting |
| Burst | burst 100k | variable | 256 | queue recovery |

For slow-consumer correctness use gates/channels where possible. Do not make correctness depend on fragile `Task.Delay` timing.

---

# 8. Failure profiles

Failures must be deterministic:

- every Nth item fails;
- fail first K attempts then succeed;
- always fail;
- cancel after N accepted items;
- cancel while producer is blocked;
- cancel while sink is blocked;
- dispose concurrently from N callers;
- fault during initialization;
- fault during operation plus fault during cleanup.

Validate both outcome and resource counts before using timings.

# 11. Regression policy

## Phase 1 — evidence only

Until the lab has enough history:
- no hard wall-clock PR failure threshold;
- flag changes for review;
- allocations/boundedness/lifecycle invariants may be hard gates immediately;
- exact correctness mismatch is always failure.

## Phase 2 — controlled-runner gates

After at least several stable reference runs:
- per-scenario thresholds, not one global “10%” rule;
- practical significance floor;
- repeated/counter-balanced A/B evidence;
- regression requires reproducibility before release blocking.

Example policy classes:
- Core hot path: tight threshold;
- integration CPU/allocation: moderate threshold;
- disk/provider/network latency: informational;
- startup: evaluate separately from steady state;
- soak: slope/leak invariant rather than raw latency.

Never optimize to one aggregate score.

# 14. Acceptance criteria for the lab

The lab is accepted when:

1. baseline package hashes are verified;
2. full SP220-01…12 candidate SHA is immutable and recorded;
3. same harness SHA is used for both targets;
4. every strict A/B scenario has a correctness oracle;
5. API-different comparisons are labeled evolution rather than strict regression;
6. v220-only scenarios cannot emit a fake 2.1.2 ratio;
7. BenchmarkDotNet raw artifacts are retained;
8. memory/allocation data is collected;
9. stress workloads are deterministic/replayable;
10. 32-run concurrency suite passes;
11. 1000-run lifecycle suite passes where applicable;
12. soak ends with zero active SmartPipe runs/resources;
13. environment fingerprint is embedded in every result set;
14. GitHub-hosted results are not used as authoritative hard wall-clock gates;
15. a suspicious regression can be escalated to trace/gcdump evidence;
16. final report distinguishes speed, allocation, scalability, lifecycle robustness and deliberate trade-offs.

---

# 15. Explicit anti-patterns

Forbidden:

- comparing different benchmark source revisions and calling the delta a product improvement;
- comparing moving branch names without recording SHA;
- using one run;
- changing data shape between A and B;
- changing SDK/runtime between A and B without labeling it a toolchain experiment;
- using Debug builds;
- measuring setup accidentally inside a steady-state benchmark;
- comparing file/database/network latency across uncontrolled hosts as a hard gate;
- treating p95 from tiny sample counts as meaningful;
- hiding failed correctness checks and still publishing timings;
- combining startup and steady-state into one number;
- using GitHub-hosted timing noise as a release blocker;
- forcing every scenario into an A/B ratio when 2.1.2 had no equivalent capability.
