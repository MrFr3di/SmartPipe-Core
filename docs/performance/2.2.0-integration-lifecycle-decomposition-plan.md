# SmartPipe 2.2.0 integration lifecycle decomposition plan

Date: 2026-09-21

## Why this follow-up exists

The first evolution passes for Dapper and Entity Framework Core are functionally green but show a large absolute gap between the legacy 2.1.2 selector path and the 2.2.0 runtime-owned pipeline path.

Those results are not strict regressions because the lifecycle contracts differ. Re-running the same full query workload will not explain the cost. The next lab must decompose the candidate path.

### Generic 2.2.0 run baseline

The v2.2-only definition-model pass measured a warm zero-stage start/completion at approximately:

- 17.874 µs;
- 11.447 KiB/op.

That value is not directly subtractable from the database integration runs because the benchmark fixtures and invocation shapes differ. It does, however, prove that generic run activation is a meaningful fixed-cost component and motivates a controlled decomposition in one benchmark process.

## Hypothesis to test

The observed integration cost consists of at least four components:

1. **database/provider work** — connection/context/query execution;
2. **SmartPipe source activation** — runtime-owned source/context/connection creation;
3. **generic PipelineRun lifecycle** — run allocation, completion, cancellation/error plumbing and cleanup;
4. **per-result adaptation** — envelope/result creation and result-stream consumption.

The current one-row versus 100-row evidence suggests both a fixed component and a row-count-dependent component. This is a hypothesis, not yet a measured attribution.

## Dapper decomposition workload

Use one immutable SmartPipe 2.2.0 target and one deterministic named shared in-memory SQLite database. Pin Microsoft.Data.Sqlite and Dapper to the exact package versions already used by the evolution pass.

Measure in the same process:

- `RawDapper_Single`: fresh connection + parameterized Dapper query + materialize one row;
- `RawDapper_100`: fresh connection + Dapper query + materialize 100 rows;
- `SourceOnly_Single`: activate the SmartPipe Dapper source and consume it directly, without PipelineRun, if this can be done through public API; otherwise omit rather than using internals;
- `SourceOnly_100`: same for 100 rows;
- `PipelineRun_Single`: current public 2.2.0 QuerySource + PipelineRun path;
- `PipelineRun_100`: current public 2.2.0 QuerySource + PipelineRun path.

If source-only activation cannot be expressed through public APIs, the lab must not use internal runtime APIs merely to manufacture a decomposition point.

## EF Core decomposition workload

Use one open SQLite in-memory connection and Microsoft.EntityFrameworkCore.Sqlite 10.0.11 on every method.

Measure:

- `RawEf_Single`: fresh DbContext + AsNoTracking filtered query + one row;
- `RawEf_100`: fresh DbContext + AsNoTracking ordered query + 100 rows;
- optional source-only paths only if public API supports them;
- `PipelineRun_Single`;
- `PipelineRun_100`;
- `CompiledPipelineRun_Single`;
- `CompiledPipelineRun_100`.

The compiled-query path is important because the 2.2.0 package explicitly exposes `CompiledQuerySource`; it should be characterized separately rather than inferred from normal-query results.

## Measurements

For every method retain:

- mean/median/stddev;
- allocations/op;
- A-B-B-A or repeated same-target order as applicable;
- exact item count/checksum;
- first-row latency where a public instrumentation point can be measured without changing semantics;
- total completion time;
- exact cleanup/disposal gates.

For candidate-only decomposition, report absolute values and within-version ratios only. Do not present them as 2.1.2 regression percentages.

## Acceptance logic

The decomposition is successful if it can answer:

- how much of the single-row cost remains after removing database/provider work;
- how much extra cost appears between one and 100 rows;
- whether that row-count slope is primarily SmartPipe result wrapping/streaming;
- whether compiled EF queries materially change the candidate integration cost;
- whether allocations are predominantly fixed per run or scale with row count.

## Optimization rule

Do not change production code solely because the full evolution benchmark is slower.

Only optimize after the decomposition identifies a concrete dominant cost with a plausible application scenario. Preserve runtime ownership, cancellation, completion, error propagation, cleanup and public API semantics unless evidence shows a cheaper implementation can retain those guarantees.
