# SmartPipe 2.2.0 comparative lab — engineering summary

Date: 2026-09-21

## Scope

Baseline:

- SmartPipe 2.1.2;
- product SHA `8e79902d22de714f493582946f7c260462b0895e`.

Candidate:

- SmartPipe 2.2.0 SP220-01..11;
- product SHA `61ceef6bf69aef0a4f79b25384352d238979200f`.

SP220-12 / Mapster is excluded from this lab revision.

The lab distinguishes three evidence classes:

- **strict A/B** — same semantics and shared workload source; cross-version deltas are allowed;
- **evolution** — same product goal but materially changed lifecycle/API semantics; side-by-side absolute values only;
- **v2.2-only** — no honest 2.1.2 equivalent; absolute and intra-version characterization only.

GitHub-hosted timing is informational. Package provenance, correctness, lifecycle, deterministic disposal, boundedness and exact result oracles are hard evidence.

## High-confidence positive results

### Package modularization works

The package-footprint evidence supports the architectural goal of SP220-01.

Representative focused 2.2.0 consumers generally move from the broad three-SmartPipe-package / nine-external-dependency closure of `SmartPipe.Extensions 2.1.2` to two or three SmartPipe packages and one to four external dependency IDs.

Examples of compressed SmartPipe closure:

- DI: 331.6 KiB → 226.2 KiB;
- Hosting: 331.6 KiB → 254.1 KiB;
- OpenTelemetry: 331.6 KiB → 205.8 KiB;
- Channels: 331.6 KiB → 208.6 KiB;
- Dapper: 331.6 KiB → 240.1 KiB;
- EF Core: 331.6 KiB → 224.4 KiB.

This is dependency isolation / deployment-shape evidence, not runtime-speed evidence.

### Lifecycle robustness is currently green

Expanded deterministic Core stress passed on both versions:

- exact successful-item counts and checksums;
- 32/32 deterministic cancellations;
- 1000/1000 deterministic source failures;
- exact source/stage/sink disposal counts;
- zero final active/pending work.

No lifecycle correctness or cleanup regression was found in the covered profiles.

### JSON and CSV package splits are performance-neutral in the tested paths

JSON strict pass:

- allocations unchanged on all four source-generated/options round-trip methods;
- repeatable methods remain roughly within ±3%;
- no material systematic timing regression.

CSV strict pass:

- small round-trip: +0.33% time, -0.05% allocation;
- medium round-trip: +1.37% time, +0.27% allocation.

These are not release-blocking changes on hosted runners.

Two independent strict Short passes now exist.

`ConditionalTrueTransform`:

`CompositeThreeTransforms`:

### ChannelMerge allocation

Their current hosted timing must not be used for an optimization or release decision.

## Evolution-cost findings

The following are real absolute costs, but not strict regressions because 2.2.0 provides additional ownership/lifecycle semantics.

### Dependency Injection

2.2.0 adds keyed registration, canonical registry, run registry/observation state and per-run scope ownership.

The pass shows higher absolute provider-build and run allocation/cost. This should be treated as architecture-cost tracking, not as an apples-to-apples percentage regression.

### Hosting

The 2.2.0 start/stop path is substantially more expensive than the 2.1.2 generic hosted-service path.

The new candidate path includes:

- keyed multi-pipeline orchestration;
- ordered startup;
- rollback bookkeeping;
- reverse shutdown;
- run/scope ownership.

The correct next step is fixed-cost decomposition, not removal of those guarantees.

### Dapper

Full-query evolution pass:

| Workload | 2.1.2 | 2.2.0 |
| --- | ---: | ---: |
| Single row | 31.663 µs / 2.96 KiB | 99.731 µs / 14.95 KiB |
| 100 rows | 167.162 µs / 26.34 KiB | 440.190 µs / 55.42 KiB |

The gap is too large to dismiss as runner noise, but the operation is not semantically equivalent. A candidate-only Raw-Dapper vs PipelineRun decomposition is being added to isolate the actual SmartPipe layer.

### Entity Framework Core

Relational SQLite pass, with both sides pinned to EF Core SQLite 10.0.11:

| Workload | 2.1.2 | 2.2.0 |
| --- | ---: | ---: |
| Single row | 143.526 µs / 60.15 KiB | 420.247 µs / 74.38 KiB |
| 100 rows | 303.698 µs / 102.26 KiB | 866.607 µs / 134.01 KiB |

The provider/version/query semantics are aligned, so the larger absolute candidate cost is real enough to decompose. It is still not a strict regression result because context ownership and PipelineRun semantics differ.

## Definition-model baseline for future releases

The v2.2-only public-API characterization establishes a useful future baseline.

Representative candidate costs:

- build zero-stage definition: ~407 ns / 1.586 KiB;
- build ten-stage definition: ~3.711 µs / 9.211 KiB;
- warm zero-stage start+complete: ~17.874 µs / 11.447 KiB;
- warm ten-stage start+complete: ~50.281 µs / 21.839 KiB.

This indicates a meaningful fixed per-run cost plus additional per-stage work.

It should be used to compare future 2.2.x/2.3.x changes, not to manufacture a 2.1.2 ratio.

## Current engineering priorities

### P0 — complete long-duration lifecycle evidence

Finish the first 30-minute Core soak and inspect:

- active runs final = 0;
- created components = disposed components;
- errors = 0;
- ThreadPool pending work final = 0;
- post-warmup managed/GC heap/working-set trend;
- handle/fd trend.

Do not infer leak/no-leak from the 30-second verify profile.

### P1 — decompose Dapper and EF lifecycle cost

Measure raw database work and PipelineRun work in the same candidate process and fixture.

For Dapper, the raw path must use the same Dapper `ExecuteReaderAsync` primitive and row mapper as the SmartPipe source.

For EF, use the same SQLite provider/version and no-tracking query shape. Add the public compiled-query source path separately.

### P1 — profile CompositeTransform

The strict slowdown is directionally reproduced across two passes. A focused characterization should isolate:

- child invocation cost;
- lifecycle/state checks;
- cancellation/token plumbing;
- loop/state-machine overhead.

Do not remove lifecycle correctness checks without evidence that the replacement preserves their guarantees.

### P2 — confirm low-risk strict lanes

A second JSON and CSV Short can improve confidence, but neither is currently a priority because pass 1 is near parity and allocations are stable.

## Current decision

The lab does **not** support a claim that SmartPipe 2.2.0 is globally slower or globally faster than 2.1.2.

It does support narrower conclusions:

- package modularization materially improves dependency closure for focused consumers;
- tested correctness/lifecycle/disposal invariants are preserved;
- JSON/CSV legacy-compatible paths are effectively stable;
- ConditionalTransform is reproducibly faster;
- CompositeTransform is reproducibly slower and deserves profiling;
- two-reader ChannelMerge has a reproducible small allocation increase;
- the richer 2.2.0 DI/Hosting/database integration lifecycle has measurable fixed cost that must be decomposed rather than mislabeled as a strict regression.

Release or optimization decisions should be made from those scoped findings, not from a single aggregate score.
