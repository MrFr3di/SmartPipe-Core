# SmartPipe 2.2.0 release notes

SmartPipe 2.2.0 completes the move from a broad integration package toward a
modular package ecosystem while keeping `SmartPipe.Core` as the single runtime
engine. New applications should reference only the integration leaves they use.
`SmartPipe.Extensions` remains the 2.2 compatibility facade/bundle for
applications that intentionally want the broad integration set.

## Highlights

- Immutable typed pipeline definitions with explicit pipeline/stage identity,
  per-run activation, ownership descriptors, deterministic rollback, and
  reusable all-factory definitions.
- Dedicated DI, Generic Host, HealthChecks, and exporter-neutral OpenTelemetry
  packages.
- Narrow Channels, Transforms, DataAnnotations, Logging, CSV, Dapper, Entity
  Framework Core, Mapster, HTTP, HTTP.Json, and Polly packages.
- Optional `SmartPipe.Extensions.PostgreSql` for binary COPY and
  `LISTEN`/`NOTIFY` over an application-owned `NpgsqlDataSource`.
- `SmartPipe.Testing` for framework-neutral test helpers without adding a
  production dependency.
- Release hardening for package ownership, locked restores, source provenance,
  packed consumers, trimming/NativeAOT claims, Windows/Linux validation, and
  immutable release artifacts.

## Release integrity

The 2.2.0 release path is explicit and main-driven. Creating or pushing a
`v*` tag does not publish packages. The maintainer first runs the release
workflow from the accepted `main` commit with `publish_nuget=false`; this
full dry run performs release validation without creating a NuGet publication,
tag, or GitHub Release.

The release path builds the package set once as an immutable producer artifact
and records the source commit, validation mode, version, package inventory,
archive hashes, `SHA256SUMS`, and the exact dated 2.2.0 changelog section as
`RELEASE_NOTES.md`. Windows validation and PostgreSQL package consumers replay
that same producer artifact instead of repacking it.

After the dry-run evidence is accepted, `publish_nuget=true` authorizes the
publication run. Publication and recoverable re-runs revalidate the recorded
package and symbol payloads before publishing. An existing package is accepted
for recovery only after payload equivalence is proven; a conflicting or changed
payload fails closed. The publisher attests the validated package archives and
obtains its short-lived NuGet credential only after Linux, Windows and
PostgreSQL release gates succeed.

Only after NuGet publication is verified does the final release job create
`v2.2.0` on that exact source commit. It then creates a draft GitHub Release,
attaches the validated package/symbol/checksum assets, uses
`RELEASE_NOTES.md` as the release body, and publishes the draft. Published
release tags are never moved or reused.

## Compatibility with 2.1.2

The immutable 2.1.2 facade baseline contains 42 relevant public identities.
For 2.2.0, 23 are preserved through type forwarding, 13 remain physically in
the compatibility facade, and six are intentionally removed.

The removed identities are:

- `HttpSelector<T>`
- `HttpClientFactorySelector<T>`
- `HttpSink<T>`
- `HttpClientFactorySink<T>`
- `HttpSelectorStreamingMode`
- `PollyResilienceTransform<T>`

Those six require migration and recompilation. Retained identities are covered
by the compatibility matrix and old-binary consumer validation; namespace
preservation alone is not treated as binary compatibility evidence.

## Upgrade

For a minimal Core application:

```bash
dotnet package add SmartPipe.Core --version 2.2.0
```

For a narrow integration, add the owning leaf directly, for example:

```bash
dotnet package add SmartPipe.Extensions.Json --version 2.2.0
dotnet package add SmartPipe.Extensions.Http --version 2.2.0
```

Applications intentionally retaining the broad compatibility facade can update
it directly:

```bash
dotnet package add SmartPipe.Extensions --version 2.2.0
```

Update explicit SmartPipe package references together. Do not add
`SmartPipe.Testing` to production dependencies. `SmartPipe.Extensions.PostgreSql`
is optional and is not pulled in by the facade.

## Detailed changes

The repository [CHANGELOG](../../CHANGELOG.md) is the curated chronological
record for runtime fixes, performance work, package extraction, integration
semantics, and release hardening included in 2.2.0. At final release preparation
its `## [2.2.0] - YYYY-MM-DD` section becomes the GitHub Release body
verbatim through the generated `RELEASE_NOTES.md`; Git history or generated PR
lists are not the authoritative public release notes.
