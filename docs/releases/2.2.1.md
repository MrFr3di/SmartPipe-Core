# SmartPipe 2.2.1 servicing notes

SmartPipe 2.2.1 is the first servicing release after the published 2.2.0
package set. Its scope includes backward-compatible correctness, privacy, reliability,
performance and release-engineering hardening. It preserves the 2.2.0 package
architecture and contains additive, opt-in runtime policy APIs under the
explicit 2.2.1 versioning exception; existing policy defaults remain unchanged.

## Current servicing scope

- Centralize the current release prefix and previous-stable baseline in
  `eng/SmartPipe.Versions.props`; package projects, package validation and
  release tooling consume that single machine-readable version catalog.
- Seal the public API that shipped in 2.2.0 as the analyzer baseline.
- Use the published 2.2.0 package set as the immediate Package Validation
  baseline for every package in the synchronized 2.2.1 train.
- Keep the immutable 2.1.2 baseline as historical evidence for the 2.2
  migration rather than as the servicing baseline.
- Keep CodeQL action phases on one version and group their Dependabot updates.
- Correct post-release support, security, SDK, and release documentation.
- Stop the legacy Dapper source completion log from emitting raw SQL text at
  Information level.
- Keep Entity Framework Core default failure logs payload-free: SmartPipe logs
  outcome metadata without attaching provider exception details, while the
  original exception still propagates to the caller.

## Runtime I/O additions and behavior

The runtime I/O work in merged PRs #155–#158 adds the following capabilities to
`SmartPipe.Core`. The opt-in APIs are recorded in `PublicAPI.Unshipped.txt` before
publication; the published 2.2.0 `PublicAPI.Shipped.txt` is not regenerated.

| Feature | Configuration | Existing default and boundaries |
| --- | --- | --- |
| Shared retry budget | `PipelineRuntimeOptions.RetryBudget = new RetryBudgetOptions(capacity, refillTokensPerSecond)` | `null`: no shared per-run budget; existing retry policy limits still apply. Zero refill grants only the initial capacity for the run. |
| Retry jitter | `RetryPolicy.Jitter = RetryJitterMode.Full` | `None`: deterministic retry delay. Full samples one delay below the calculated capped delay. |
| Timed-attempt admission | `PipelineRuntimeOptions.TimedAttemptAdmission = new TimedAttemptAdmissionOptions(maxOutstandingAttempts, TimedAttemptAdmissionMode.Wait)` | `null`: no admission cap. Active and detached timed executions count together; Wait is deadline/cancellation-aware, Reject is a terminal admission failure. |
| Circuit-breaker sampling | `CircuitBreakerPolicy.SamplingMode = CircuitBreakerSamplingMode.Bucketed` or `CircuitBreakerOptions.SamplingMode = CircuitBreakerSamplingMode.Bucketed` | `Exact` remains the default. `SamplingBucketCount` defaults to 64 when bucketed is selected; oldest partial-bucket inclusion introduces less than one bucket width of temporal overhang, not a bounded failure-ratio error. |

The processing supervisor, exact sampling expiry and output/observer fast paths
are internal changes. Producer-error precedence, worker and detached-attempt
ownership, observer delivery contracts, sink writes and telemetry remain guarded
by runtime regressions. Opt-in admission can reduce concurrency when a timed
operation ignores cancellation; it cannot forcibly terminate user code.

Paired benchmark evidence is archived in the [runtime I/O report](../../benchmarks/SmartPipe.Benchmarks/RuntimeIo-results.md)
and [circuit-breaker sampling report](../../benchmarks/SmartPipe.Benchmarks/CircuitBreakerSampling-results.md).
Those observations are tied to their benchmark configuration, not universal
throughput or p99 guarantees.

## Compatibility with 2.2.0

The 2.2.1 line has no intentional public API break relative to the published
2.2.0 packages. Package Validation and PublicApiAnalyzers guard that contract.
The 2.1.2 compatibility evidence remains preserved separately for the original
2.2 transition.

See the [2.2.0 → 2.2.1 compatibility note](../reference/compatibility/2.2.0-to-2.2.1.md)
and the [2.2.0 → 2.2.1 servicing migration](../migration/2.2.1-integration-packages.md).

## Detailed changes and release status

The repository [CHANGELOG](../../CHANGELOG.md) is the authoritative source for
the release body extracted by the publishing workflow. Preparing a dated 2.2.1
section does **not** publish any NuGet package, tag or GitHub Release. Release
acceptance requires an independent release-mode dry run and an explicit
publication decision as tracked in [REL221-01](https://github.com/MrFr3di/SmartPipe-Core/issues/159).
If actual publication occurs after the dated changelog entry, update that date
in the release preparation PR before dispatching publication.
