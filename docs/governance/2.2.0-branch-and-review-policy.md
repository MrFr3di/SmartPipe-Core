# SmartPipe 2.2.0 branch and review policy

This policy governs every SP220 EPIC and pull request targeting the 2.2.0 release. The architecture decisions are normative in [ADR-0001](../adr/0001-smartpipe-2.2-package-boundaries.md); the [master architecture plan](../plans/2.2.0-extension-architecture.md) defines the release scope, and the [SP220-00 detailed plan](../plans/2.2.0/SP220-00-governance-and-baseline.md) defines baseline evidence.

## Baseline and branch graph

The exact reviewed baseline is `8e79902d22de714f493582946f7c260462b0895e`.

```text
main
  └── release/2.2.0
        ├── sp220/00-governance
        ├── sp220/01-package-infrastructure
        ├── sp220/02-core-definition
        └── sp220/<EPIC>-<short-name>
```

- `release/2.2.0` is the protected integration branch.
- Task branches start from the current `release/2.2.0` and target it by pull request.
- The final release pull request targets `main` from `release/2.2.0` after full release validation.
- Direct pushes, force pushes, rebases, history rewrites, and deletion of `release/2.2.0` are prohibited.
- A task branch is deleted after merge.
- Use a harness-managed worktree when provided. If repository-local worktree roots are not ignored, use an external worktree under `C:\tmp`; do not change `main` merely to enable local worktrees.

## Exact-head CI evidence

Baseline and release-candidate evidence must identify the exact candidate commit. Dispatch CI against a branch or tag ref that points to the candidate SHA, obtain the resulting workflow run, and accept it only when the returned `headSha` exactly equals the candidate SHA. A successful run for an ancestor, another ref, or an earlier branch head is not evidence. Record the candidate SHA, run ID, URL, event, status/conclusion, SDK, and every required check in the baseline or release report.

## Branch ruleset

The repository owner or administrator applies and verifies an active GitHub ruleset (or the closest equivalent branch-protection rule when rulesets are unavailable):

| Setting | Required value |
|---|---|
| Target | Exact match `release/2.2.0` |
| Restrict deletions | Enabled |
| Block force pushes | Enabled |
| Require pull request | Enabled |
| Required approvals | At least 1; 2 for Core, public API, CI, or security changes when a second qualified reviewer is available |
| Dismiss stale approvals | Enabled |
| Review latest push | Required |
| Conversation resolution | Required |
| Status checks | Required |
| Branch currentness | Required, or enforced by merge queue |
| Checks | `CI / validation`, Windows JSON lane, CodeQL, Dependency Review, baseline contract |
| Linear history | Disabled while merge commits are required for reviewed hotfix synchronization |
| Bypass | Repository owner only; audited as described below |

Ruleset application is an owner/admin gate. Do not report it complete without recording the ruleset name, numeric ID, target, enforcement status, required checks, bypass actors, and verification date. Missing or inactive protection keeps the pull request non-mergeable.

## Pull request targets and merge strategy

- Every SP220 task/EPIC pull request targets `release/2.2.0`; it must not target `main` directly.
- The integration branch accepts a reviewable merge commit or repository-configured merge-queue result. Squash/rebase must not erase evidence required by an approved EPIC plan.
- After the first merged EPIC, `release/2.2.0` is never rebased or force-updated.
- A hotfix first merged to `main` is synchronized into `release/2.2.0` by an explicit merge commit after conflict, compatibility, and validation review. Never cherry-pick or silently replay it without documenting why the branches differ.

## Required reviewer categories

Every pull request requires a maintainer reviewer. Add the following qualified categories when their surface changes:

| Change surface | Required reviewer category |
|---|---|
| Core runtime, async lifecycle, cancellation, ownership | Core/runtime maintainer |
| Public API, namespaces, forwarding, package boundaries | API/package compatibility maintainer |
| Workflows, repository checks, release, credentials, dependency policy | CI/release or security maintainer |
| DI, Hosting, telemetry, transport, or data integration | Maintainer for the affected integration domain |
| User-facing contract or migration guidance | Documentation/consumer-experience reviewer |

One reviewer may satisfy multiple categories when qualified. Author self-review does not replace required independent approval.

## Commit naming and scope

Prefer one reviewable commit per task or a small ordered TDD sequence. Allowed prefixes for SP220-00 are `docs:`, `chore(governance):`, `build(baseline):`, `test(baseline):`, and `ci(baseline):`; later EPICs use the repository's conventional prefixes with an explicit scope. Messages such as `update`, `misc`, or `fix stuff` are prohibited. Do not mix governance, runtime refactoring, package movement, and unrelated cleanup. A reviewed commit changed after approval requires fresh review.

## Generated files and artifacts

- Never commit `.nupkg`, `.snupkg`, `artifacts/`, build output, temporary worktrees, credentials, or machine-specific paths.
- Commit a generated source, manifest, schema, snapshot, or API baseline only when its owning plan names it, generation is deterministic, and the pull request includes the generator/input and validation evidence.
- Review generated diffs for unexpected API, dependency, identity, path, timestamp, or ordering drift. Canonical hashes must exclude environment-sensitive data.

## Emergency bypass audit

Only a repository owner may use a configured bypass. Before merge when possible, otherwise immediately afterward, the pull request must record:

- actor, timestamp, and ruleset/rule ID;
- incident or business reason and why the normal gate could not be used;
- exact commits and checks bypassed;
- risk assessment, approvals obtained, and affected packages/APIs;
- compensating validation and its results;
- follow-up issue, owner, and due date.

Bypass never permits force-pushing or deleting `release/2.2.0`, suppressing evidence, or claiming a skipped check passed.

## Definition of ready, review, and done for every EPIC

These gates apply to each SP220 EPIC in addition to its detailed plan.

### Ready

- Scope, non-goals, dependencies, baseline commit, affected files/projects, and compatibility constraints are explicit with no unresolved TBDs.
- Required reviewer categories and CI/consumer gates are identified.
- The task branch starts from the current integration branch in an isolated worktree and is clean.
- Existing runtime/API behavior is located in source and tests; the smallest deterministic validation path is known.

### Review

- The pull request targets `release/2.2.0`, contains only the EPIC scope, links its plan/ADR, and explains compatibility, package-graph, AOT/trimming, security, and lifecycle effects as applicable.
- Required reviewer categories approve the current head; all conversations are resolved.
- Required checks attach to the exact pull-request head and pass. Generated files, public API changes, dependencies, and type movement receive explicit diff review.
- Deviations from architecture MUST/MUST NOT rules have an accepted superseding ADR rather than an undocumented exception.

### Done

- The approved head is merged through the configured strategy without rewriting integration history, and the task branch is removed.
- The EPIC acceptance tests and proportional validation ladder pass; evidence is linked and exact-head where required.
- Public docs, API baselines, package allowlists, migration/consumer tests, and release records are updated when the EPIC changes their contract.
- Deferred work has a tracked owner and target; no hidden TODO/TBD or unreviewed generated/binary artifact remains.

## Policy changes

Changes to this policy use a dedicated governance pull request into `release/2.2.0`, name the affected controls, preserve or strengthen auditability, and obtain a maintainer plus any relevant CI/security or API/package reviewer. Architecture changes additionally follow ADR-0001's supersession policy.
