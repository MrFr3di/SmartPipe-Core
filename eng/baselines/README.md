# Reproducible baseline files

This directory contains the versioned schema and canonical snapshots used to verify the SmartPipe 2.1.2 compatibility baseline for the 2.2.0 release.

`manifest.json` and snapshot files are generated by `capture-baseline`; do not edit them manually. `provision-baseline` is the explicit acquisition boundary and may use the network to fetch the manifest's package set. Verification is deterministic and offline after required artifacts have been provisioned.

`verify-baseline --offline` never acquires packages or touches the network. The legacy `verify-baseline` invocation without `--offline` remains available for 2.2.0 compatibility and provisions first, then runs the same offline verification; workflows use the explicit provision-plus-verify split.

Verification profiles remain a closed set of offline repository checks and currently contain no baseline check. A future profile adapter must accept only offline verification; package acquisition stays outside profile composition.

`baseline-report.md` is generated deterministically before `manifest.json` and summarizes the exact capture commit, each accepted workflow head SHA, and package/snapshot hashes. Verification requires its bytes to match the manifest-derived report.

Manifest producers must persist manifests through `BaselineManifestSerializer.WriteAsync`; it is the supported write boundary and emits the canonical bytes returned by `SerializeToUtf8Bytes`. The string `Serialize` API is retained for comparison and diagnostics, not direct file output.

Canonical JSON uses schema version 1, UTF-8 without a BOM, two-space indentation, LF line endings, exactly one final LF, explicit property order, and stable identity ordering for arrays. Text hashes normalize a leading UTF-8 BOM and CRLF/CR to LF without trimming whitespace; package hashes cover the original package bytes.

The manifest rejects unknown properties and schema versions. `repository.captureCommitSha` and every workflow `headSha` must be the same lowercase 40-character SHA captured from a clean HEAD. Package sources and workflow evidence URLs must use HTTPS, hashes must be lowercase SHA-256, and snapshot paths must be repository-relative without parent traversal.

## Verification diagnostics

`verify-baseline --offline` reports deterministic diagnostics sorted by code and message:

- `SPB001`: unsafe or invalid manifest/schema/path;
- `SPB002`-`SPB004`: repository identity, capture-commit ancestry/availability, or SDK mismatch;
- `SPB005`-`SPB006`: required file missing or snapshot hash mismatch;
- `SPB007`-`SPB010`: package hash, signature, identity/assets, or dependencies mismatch;
- `SPB014`: public API snapshot mismatch;
- `SPB015`: repository dependency snapshot mismatch;
- `SPB016`: required release branch missing from CI, CodeQL, or Dependency Review workflow policy.

Offline verification never fetches packages. It requires the capture commit to exist and be an ancestor of current HEAD, failing closed for unrelated or missing/shallow history. It hashes package bytes before signature or archive inspection and ignores unreferenced files in the baseline directory.

Capture consumes the literal JSON array produced by `gh run list --json databaseId,workflowName,headSha,status,conclusion,url,event,createdAt`. Every returned run must target the requested capture commit; that `headSha` is retained in each workflow manifest entry, and exactly one completed successful run is required for each of CI, CodeQL, and Dependency Review. Workflow policy verification uses a bounded parser for the repository's current YAML shape and checks `release/2.2.0` in the actual `on.push.branches` and/or `on.pull_request.branches` lists; comments, environment values, and step text do not count.
